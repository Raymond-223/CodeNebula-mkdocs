# Git Workflow

Git 最重要的不是命令数量，而是理解三个动作：**保存一个可回退的版本、在独立分支上修改、把变化安全合并回来**。

大多数 Git 焦虑都来自一个误解：把 Git 当成“上传代码的工具”。一旦这样理解，命令就变成了需要背诵的咒语，冲突变成了必须消灭的障碍，历史变成了没人看的噪音。反过来，把 Git 当成**一份带有分支的时间线系统**，每个动作的动机就都清楚了：commit 是给时间线打一个可回溯的标记，branch 是让时间线暂时分叉，merge/rebase 是把分叉接回去。理解了这三件事，命令只是表达方式。

本文按“快照 → 隔离 → 合并 → 审查 → 回退 → 诊断”的顺序展开，并补上三个工程实践中绕不开的话题：不同分支策略的取舍、改写历史的代价、仓库卫生。读完之后，你应该能回答一个很实际的问题：**当线上出问题、需要定位和回退时，你的 Git 历史能不能支持这件事？**

## Commit 是一次有意义的状态快照

工作区文件不断变化，`git add` 选择本次要记录的变化，`git commit` 把它们保存为一个可追踪版本。

理解“快照”这个词很关键：commit 记录的不是“我改了什么”，而是“此刻整个项目长什么样”。`git diff` 之所以能算出任意两个 commit 之间的差异，正是因为每个 commit 都保存了完整状态。这也解释了为什么 Git 的回退那么可靠——它不是把改动反向应用一遍，而是直接切到另一个已知状态。

最小工作流：

```bash
git status
git add src/ tests/
git commit -m "fix planner boundary handling"
```

好的 commit 应该只做一件相对完整的事。把“改 UI、重构算法、更新依赖、修测试”全部塞进一次提交，会让代码审查和回退都变困难。

“一件完整的事”有个可操作的判据：**如果这个 commit 被单独回退，系统是否仍然处于一个说得通的状态？** 如果回退之后代码无法运行（比如接口改了但调用方没改），说明这次提交切得太细或太碎；如果回退之后要连带撤销三件不相干的功能，说明这次提交切得太粗。

提交信息也值得当成接口来写，因为它面向的读者是未来的自己和同事。一条有用的信息要回答“改了什么”和“为什么改”，第二点尤其重要——代码本身已经说明了改了什么，但无法说明动机。

| 提交信息部分 | 内容 | 反例 |
| --- | --- | --- |
| 类型 | feat / fix / refactor / test / docs | 无类型，直接写“更新” |
| 范围 | 受影响模块 | 所有提交都写“多个文件” |
| 摘要 | 一句话说明行为变化 | “修改代码”“fix bug” |
| 正文 | 为什么改、有何取舍 | 只有摘要，动机丢失 |
| 关联 | issue / PR 编号 | 无法追溯需求来源 |

## Branch 的意义是隔离正在进行的修改

创建功能分支：

```bash
git switch -c feature/task-api
# 修改并提交
git switch main
git merge feature/task-api
```

分支并不是完整复制一份项目，而是让不同提交历史可以暂时分开发展。它最有价值的场景是：主分支继续保持可用，同时新功能、实验或修复可以独立进行。

理解这一点可以避免两个常见误解。第一，分支不是备份——它和你当前的工作区共用同一个仓库，误操作分支并不能救回没提交的文件。第二，分支不是越多越好——每个长期存在的分支都是一份需要同步的债务，分叉时间越长，合并时的冲突面越大。

分支命名本身也是一种沟通。用 `feature/`、`fix/`、`hotfix/`、`chore/` 前缀，可以让别人在分支列表里一眼看出意图；把 issue 编号写进去（`feature/task-api-142`），则把分支和需求关联了起来，回溯时不必靠记忆。

关于分支生命周期的实用建议是：**尽量短**。一个分支存活两三天、只改动几百行，合并过程通常是顺利的；存活两周、改动上千行，合并就会变成一次需要专门安排时间的工程活动。缩短分支寿命的最有效手段不是更努力地写代码，而是把大功能拆成多个可以独立合并的小步骤（例如先加字段，再加逻辑，最后接 UI）——这也正是“每次提交只做一件事”在分支层面的延伸。

## Git 冲突处理

两个人修改同一段代码时，Git 可能无法自动判断应该保留哪一边。此时需要人工理解上下文，然后重新测试。

冲突的本质是**两个意图在同一位置相遇**，而 Git 没有能力判断哪个意图应该胜出。它只能保留双方文本并标记出来。因此解决冲突不是文本编辑任务，而是设计判断任务：最终代码应该表达什么语义。

处理冲突的顺序应该是：

1. 看清双方分别改了什么；
2. 决定最终代码应该表达什么；
3. 删除冲突标记；
4. 运行测试；
5. 再提交合并结果。

不要只为了让冲突消失而随便选择 “ours” 或 “theirs”。这是初学者最常见的错误做法：冲突被“解决”了，但某一方的修复被静默丢弃，问题在几天后以 Bug 的形式出现，而且很难联想到当时那次合并。

更高效的做法是先理解冲突来源，再决定处理方式：

| 冲突类型 | 表现 | 建议处理 |
| --- | --- | --- |
| 相邻但无关的改动 | 同一函数不同位置 | 两边都保留 |
| 同一行不同实现 | 同一行被双方改写 | 理解意图后人工合并 |
| 结构性冲突 | 文件被移动或重命名 | 先确认文件归属再合并 |
| 生成文件冲突 | lock 文件、构建产物 | 重新生成，不要手工合并 |
| 大量格式冲突 | 换行符、缩进风格 | 先统一格式规范再重做 |

减少冲突的关键在预防，而不在解决技巧。常用的三条预防措施是：分支保持短小、避免多人同时大规模重构同一文件、把格式化改动（如全文件重新缩进）作为独立提交并约定“格式化提交不加逻辑改动”。最后一条尤其有效，因为它把“纯格式 diff”和“真实逻辑改动”分开，让冲突时的判断简单得多。

## Pull Request 与代码审查

多人协作时，常见流程是：

```text
Issue/Task → Branch → Commits → Pull Request → Review → Merge
```

代码审查主要看四件事：逻辑是否正确、接口是否清楚、测试是否覆盖关键行为、是否引入不必要复杂度。

这四件事的排序不是随意的。逻辑正确性最高优先，因为它决定合并后是否引入故障；接口清晰度次之，因为它决定未来的修改成本；测试覆盖第三，因为它是回归防护；复杂度最后，因为它最主观，也最容易引起无休止的争论。

| 审查维度 | 具体问法 | 阻塞级别 |
| --- | --- | --- |
| 逻辑正确性 | 边界与异常路径是否处理 | 阻塞合并 |
| 接口清晰性 | 命名与契约是否可理解 | 阻塞合并 |
| 测试覆盖 | 关键行为是否有断言 | 通常阻塞 |
| 安全性 | 是否有硬编码密钥或注入风险 | 阻塞合并 |
| 可读性 | 是否需要注释才能看懂 | 建议修改 |
| 风格 | 是否违背既定规范 | 交给工具 |

审查的有效性与 PR 大小强相关。研究表明，超过几百行的 PR 中，缺陷发现率会明显下降——审查者会从“逐行推理”退化为“扫一眼通过”。因此一个 PR 如果大到审查者无法建立完整心智模型，通常说明它应该继续拆小。

审查的另一半是**被审查者的准备**。一份好的 PR 描述应该包含：这个改动解决什么问题、为什么这样做、有哪些已知取舍或未覆盖场景、如何验证。这四项信息能把审查从“猜意图”变成“验证假设”，效率差别很大。

最后要说清一件事：**代码审查的目的不是找错，而是共同保证质量**。把审查意见当成对个人的评价，会让团队倾向于提交更大更少出错的改动（也就是更少评审），这恰恰适得其反。对事不对人、把理由说清楚、区分阻塞与建议，是让审查长期有效的前提。

## 分支策略与合并方式对比

分支策略的选择没有唯一正确答案，它取决于三件事：**团队规模、发布节奏、对回滚速度的要求**。小团队的痛点是流程开销，大团队的痛点是集成风险，两者的最优解往往相反。

**Trunk-based**（主干开发）的核心是：所有人尽量往 `main` 提交，分支存活时间不超过一两天，未完成的功能用 feature flag 隐藏。它的优势是集成问题被持续、小批量地解决，从不积累；代价是对自动化测试和 feature flag 机制要求较高——没有可靠测试时，主干会频繁损坏。

**GitHub Flow** 是最常见的折中：从 `main` 拉短分支，通过 PR 审查后合并，随时可发布。结构简单、工具支持好，适合大多数中小团队与持续部署的项目。

**git-flow** 引入了 `develop`、`release/*`、`hotfix/*` 等多条长期分支，用流程保证“发布版本稳定”。它的优势在需要同时维护多个线上版本（例如软件交付给不同客户）时很明显；代价是分支数量多、合并路径复杂、出错机会多。对只需要维护一个线上版本的团队，它通常是过度设计。

**Release branch** 是 git-flow 的一部分做法，但可以单独使用：从主干切出发布分支，只接受 cherry-pick 的修复。适合有明确版本号、需要回归测试周期的产品。

| 策略 | 长期分支 | 适用团队规模 | 发布节奏 | 主要代价 |
| --- | --- | --- | --- | --- |
| Trunk-based | 仅 main | 任意，需强测试 | 每天多次 | 依赖自动化与 feature flag |
| GitHub Flow | 仅 main | 2–20 人 | 数天一次 | 大改动需拆小 |
| git-flow | main + develop | 10 人以上 | 按版本发布 | 分支复杂、合并路径长 |
| Release branch | main + release/* | 5 人以上 | 定期版本 + 补丁 | 需 cherry-pick 纪律 |
| Fork + PR | main + fork | 开源 / 外部贡献 | 不定 | 上游同步成本 |

选择时的实用判据是：**如果一次合并冲突需要超过十分钟才能解决，说明分支策略和团队的集成频率不匹配**。这时应该提高集成频率（缩短分支寿命），而不是学习更高级的冲突解决技巧。

## Git 最重要的安全能力是可追溯、可回退

遇到问题时，先用 `git diff`、`git log` 看变化，再决定恢复方式。不要养成“出错就手动复制旧文件覆盖”的习惯，否则历史会失去可信度。

这里的关键词是“可信度”。如果团队成员习惯手工覆盖文件，那么 Git 历史就不再等于代码的实际演化过程——它只是一堆和现实脱节的提交。当需要排查“这个 Bug 是哪次改动引入的”时，历史就无法作为证据使用，只能靠人回忆。

因此，回退也应当走正规路径：

| 场景 | 推荐做法 | 说明 |
| --- | --- | --- |
| 工作区改错、未提交 | `git restore <file>` | 丢弃未提交改动 |
| 暂存区放错文件 | `git restore --staged <file>` | 仅取消暂存 |
| 已提交但未推送 | `git commit --amend` | 重写最后一次提交 |
| 已推送、需撤销单次改动 | `git revert <sha>` | 生成反向提交，安全 |
| 需要临时查看旧版本 | `git switch --detach <sha>` | 只读查看，不影响分支 |
| 发布版本回滚 | 回退到已知良好 tag | 优先用 tag 而非 commit |

需要强调的是 `git revert` 与 `git reset` 的区别。`revert` 是**追加一个反向提交**，历史保持完整、可审计，适合已共享的分支；`reset` 是**移动分支指针**，会让历史“消失”，只适合尚未推送的本地提交。在共享分支上使用 `reset --hard` 是团队协作中最危险的操作之一，因为它会让其他人已有的提交基础突然不存在。

对于学习和科研项目，掌握 `status / add / commit / switch / merge / pull / push / diff / log` 已经足够覆盖大多数场景。更复杂的 rebase、cherry-pick 等操作可以在真正需要时再学。

还有两个习惯值得尽早养成：一是**给发布打 tag**（`git tag v1.2.0`），让“回退目标”有稳定名字而不是一串哈希；二是**在关键节点备份远程**（确保重要提交已 push）。本地仓库虽然可靠，但硬盘损坏、误删目录这类事故只能靠远程副本恢复。

## 合并与变基的代价

merge、rebase、squash 都能把分支上的改动带进主干，但它们留下的历史形状和长期代价完全不同。选择哪一种，本质上是在“历史真实”和“历史整洁”之间做取舍。

**merge** 保留分支的分叉与汇合，产生一个合并提交。它完全忠实于实际发生的过程，且不需要改写任何已有提交，因此对共享分支最安全。代价是历史里会出现大量两条线交叉的图，`git log` 变得难以阅读。

**rebase** 把分支上的提交“重新播放”到新基底上，得到一条直线历史。它让 `git log` 非常易读，也便于二分定位；代价是**它改写了提交的身份**——每个被重新播放的提交都是新对象，哈希不同。因此对已经推送、别人可能已基于其上工作的提交做 rebase，会造成“同一份改动两份历史”的混乱。

**squash** 把分支上的多个提交压成一个再合并。它让主干每个提交都对应一个完整功能，回退时一次到位；代价是丢失了开发过程中的中间状态与尝试记录，如果某次修复需要精确定位到中间步骤，信息就不在了。

| 对比维度 | merge | rebase | squash |
| --- | --- | --- | --- |
| 历史形状 | 分叉 + 汇合 | 单条直线 | 单条直线，粒度粗 |
| 是否改写历史 | 否 | 是 | 是（仅被压的提交） |
| 冲突出现频率 | 一次（合并时） | 可能每个提交一次 | 一次 |
| 可追溯性 | 完全保留 | 保留内容，哈希改变 | 中间过程丢失 |
| 回退粒度 | 单次合并 | 单个提交 | 整个功能 |
| 适用场景 | 共享分支、长期特性 | 本地整理后再推 | PR 合并到主干 |

一条被广泛采用的实践是：**本地用 rebase 整理，共享分支用 merge**。也就是说，在把分支推给别人之前，可以自由地 rebase、amend、压缩提交，把自己的历史整理清楚；一旦推送并且有人基于它工作，就不要再改写，改用 merge 或 revert 来处理后续变化。判断标准很明确：**这段历史有没有被别人拉取过？**

还需要知道何时**不该**改写已推送历史：当主干受保护、当有其他人正在基于你的分支开发、当该提交已经被打上 tag 或已发布。在这些情况下改写历史，会让他人的 `git pull` 产生诡异的分叉和重复提交，而这类问题的排查成本极高。

若确实需要修正已推送历史的错误，更安全的替代方案是 `git revert`：它不改变既有历史，只追加一次反向修改。代价是不够“干净”，但可审计性换来的是团队的确定性——在协作环境中，这通常更值得。

## 提交历史应支持定位问题

一次提交最好只表达一个可解释的变化，并同时包含对应测试。这样二分定位、代码审查和回退都能围绕明确假设进行。把格式化、重构和行为修改混在一个巨大提交中，会显著降低 Git 历史的诊断价值。

**二分定位**（`git bisect`）是这一点的最佳说明：它通过反复检出中间提交来找出引入 Bug 的那一次改动，效率是线性排查的对数级。但它的前提是**每个提交都能编译、能运行、行为可判定**。如果历史里夹杂着“编译不过的中间状态”或“一次改动同时做了三件事”，二分的结果就会指向一个无法解释的大提交，价值大打折扣。

因此，让历史可诊断需要一些纪律：

- 每个提交独立可运行，不留下半成品状态；
- 不把重构与行为修改混在同一次提交（否则回退会连带撤销重构）；
- 提交内包含对应的测试，让二分时能自动判定好坏；
- 相关的提交用一致的命名，便于 `git log --grep` 检索；
- 大型功能拆成“加字段 → 加逻辑 → 切换使用”的可独立合并步骤。

| 历史特征 | 对诊断的影响 | 改进做法 |
| --- | --- | --- |
| 一次提交做多件事 | 二分指向无法解释的大改动 | 按意图拆分提交 |
| 提交信息无意义 | 无法用 grep 检索 | 统一信息格式 |
| 无对应测试 | 无法自动判定好坏 | 提交内附带测试 |
| 混入格式化改动 | diff 淹没真实变化 | 格式单独提交 |
| 长期不合并的大分支 | 冲突集中爆发 | 提高合并频率 |

值得强调的是，这些要求的成本其实很低——它们只是把“提交时多想十秒”变成习惯，而收益是长期的：出问题时能在几分钟内定位到具体改动，而不是几小时地翻代码猜。

## 仓库卫生与不该入库的东西

仓库里应当只放**人工维护的源文件**。构建产物可以重新生成，依赖可以重新下载，密钥可以从配置注入——把这些东西提交进去，并不会让项目更完整，只会让仓库变大、变脏、变危险。

其中风险最高的是**密钥**。一旦密钥被提交并推送，它就必须被视为已泄漏：即使下一次提交删除了它，历史里仍然完整保留。正确处置不是“删掉就好”，而是立即轮换密钥，再考虑清理历史（`git filter-repo` 等工具），并且要通知所有曾克隆仓库的人。改密钥比改历史重要得多，因为历史清理无法保证所有副本都被修正。

| 应忽略的内容 | 理由 | 错误入库的后果 |
| --- | --- | --- |
| 依赖目录 node_modules/ | 可由 lock 文件重装 | 仓库膨胀、diff 噪音 |
| 构建产物 dist/ build/ | 由源码生成 | 产物与源码不一致 |
| 编译缓存 __pycache__/ | 与机器相关 | 无用冲突、跨平台问题 |
| 虚拟环境 .venv/ | 与环境绑定 | 仓库巨大且不可移植 |
| 密钥 .env、*.pem | 敏感信息 | 泄漏，需轮换与审计 |
| 大数据集、模型权重 | 体积远超代码 | 克隆极慢，超平台限额 |
| 编辑器与系统文件 | 个人偏好 | 他人被无关 diff 打扰 |
| 日志与临时文件 | 运行时产生 | 体积增长、误提交隐私 |

**大文件**需要单独讨论，因为它们的麻烦是滞后的：Git 每个 commit 都保存完整快照，一个 100 MB 的模型文件即使之后被删除，仍然存在于历史中，克隆时依然会被下载。正确做法是使用 Git LFS（Large File Storage）或把数据放在外部存储与制品仓库中，只在仓库里保存下载脚本或校验和。

团队层面还需要 `.gitignore` 的一致性：如果每个成员各自维护忽略规则，就会出现“在 A 机器上被忽略、在 B 机器上被提交”的情况。应该把 `.gitignore` 视作项目配置的一部分，随代码一起评审更新；同时用 `git status` 在提交前确认待提交列表，这个习惯能拦住绝大多数误提交。

最后一点关于**历史清理**的认识：重写历史（删除大文件或密钥）会让所有已克隆的人需要重新克隆，代价很高。因此最划算的策略永远是**在第一次提交之前就把它挡掉**：先写 `.gitignore`，再 `git add`；先确认 `git status` 的输出，再 `git commit`。预防的成本是一分钟，修复的成本是一整个团队的重新同步。
