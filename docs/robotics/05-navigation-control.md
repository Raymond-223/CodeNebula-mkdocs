# Navigation & Control

导航不是某一个规划算法，而是一条持续运行的闭环：**定位机器人 → 理解环境 → 生成路径 → 产生局部动作 → 执行 → 再次观测。** 任何一环失效，最终表现都可能只是“机器人不走”。本章沿这条数据流逐层展开：先讲状态从哪来，再讲全局与局部如何分工，然后深入横向误差与控制律，最后给出调参顺序和实机失效模式。

## 导航首先依赖可信的机器人状态

规划器需要知道当前位置和朝向。如果定位已经漂移 2 m，后续路径即使数学上完美，也会在真实世界走错位置。因此导航问题的第一输入不是目标，而是**可靠的当前位姿**。

这一点可以用误差放大来量化。假设定位给出的位姿与真实位姿的偏差为 $\delta p$，控制器跟踪目标路径的中心线。若路径附近障碍的安全间隙只有 $d_{\text{gap}}$，那么当

$$\lVert\delta p\rVert\ge d_{\text{gap}}$$

系统就已经失去安全保证，无论后面算法多好。例如走廊宽 1.2 m、机器人宽 0.6 m，两侧各剩 0.3 m 余量；定位偏差一旦超过 0.3 m，机器人就可能擦墙。

状态估计的两个输出必须同时被使用：

- **均值** $\hat x$：用于路径跟踪与坐标变换；
- **协方差** $\Sigma$：用于判断估计是否可信。位姿协方差的对角元素超过阈值（例如 $\sigma_x>0.5\ \text{m}$）时，导航应降级为“停或慢行”，而不是继续按旧路径推进。

地图、局部障碍和机器人尺寸也必须使用一致坐标系。常见的 TF 链条是 `map → odom → base_link → sensor`；链条上任何一环断掉或时间戳早于当前时刻过多，都会让“看起来正确”的路径实际指向错误位置。

## 全局规划与局部控制

全局规划使用较稳定地图寻找从当前区域到目标的可行路线；局部控制频率更高，根据当前速度和最新障碍生成短时间速度或转向命令。

这种分层避免了两个极端：所有动态变化都让全局规划器重算会太慢，只靠局部避障又容易陷入局部最优。两层在时间尺度上分离得很清楚：

| 层 | 典型频率 | 输入 | 输出 | 时间常数 |
| --- | --- | --- | --- | --- |
| 定位/状态估计 | 50–1000 Hz | IMU、轮速、激光 | 位姿 + 协方差 | ms |
| 全局规划 | 0.5–2 Hz | 静态地图、目标点 | 全局路径 | s |
| 局部规划 | 10–20 Hz | 局部代价地图、全局路径 | 局部轨迹 | 100 ms |
| 路径跟踪控制 | 20–100 Hz | 当前位姿、目标轨迹 | 线速度、角速度 | 20–50 ms |
| 电机驱动 | 1–20 kHz | 速度指令 | 电流/占空比 | μs–ms |

**频率比至少要拉开一个数量级**，否则低层还没执行完，上层已经换了目标，闭环会持续振荡。

## 局部控制不仅要跟路径，还要满足底盘约束

差速车不能直接横移，车辆有最小转弯半径，机械平台还可能有速度和加速度限制。因此局部控制器不是简单把“下一个路径点减当前位置”当作速度命令，而要输出机器人真实可执行的控制。

对差速底盘，可执行指令是 $(v,\omega)$，而位姿演化由

$$
\begin{aligned}
\dot x &= v\cos\theta,\\
\dot y &= v\sin\theta,\\
\dot\theta &= \omega
\end{aligned}
$$

描述。直角转弯要求 $\omega\to\infty$ 或 $v\to 0$，这就解释了为什么“把目标点直接当速度方向”的朴素做法在实机上要么撞墙要么原地打转。

### 一个带限幅的 PID 控制循环

理论页解释 PID 为什么成立；工程层更关心采样、状态保存和执行器限幅：

```python
integral = 0.0
previous_error = 0.0

while robot_enabled:
    error = target_speed - measured_speed()
    integral += error * dt
    derivative = (error - previous_error) / dt
    command = kp * error + ki * integral + kd * derivative
    send_motor_command(max(-limit, min(limit, command)))
    previous_error = error
```

真实实现还应处理积分饱和、传感器超时和固定周期调度；这段代码只展示闭环中的数据流。其中三项的作用与失配症状：

| 参数 | 作用 | 偏大现象 | 偏小现象 |
| --- | --- | --- | --- |
| $k_p$ | 按当前误差响应 | 超调、高频振荡 | 响应慢、稳态误差大 |
| $k_i$ | 消除稳态误差 | 积分饱和、到达后过冲 | 恒定偏差长期存在 |
| $k_d$ | 抑制变化速率 | 放大噪声、电机抖 | 收敛慢、欠阻尼 |

差分项 $k_d$ 对噪声敏感，因为 $\dot e$ 会把测量噪声按 $1/dt$ 放大：若速度测量噪声标准差 $0.02\ \text{m/s}$、$dt=0.01\ \text{s}$，则差分项噪声幅度达 $2\ \text{m/s}$ 量级——必须加低通滤波或改用不完全微分。

## 横向误差与路径跟踪控制

路径跟踪的核心指标是**横向误差** $e$：机器人参考点到目标路径的垂直距离。它和控制量之间有明确的几何关系，Pure Pursuit 与 Stanley 是两条最常用的思路。

**Pure Pursuit（纯追踪）** 在路径上取一个离机器人前视距离 $L_d$ 的点作为目标点，把转向角对准它。设目标点在机器人坐标系下的方位角为 $\alpha$，则所需曲率为

$$\kappa=\frac{2\sin\alpha}{L_d},$$

对应前轮转角 $\delta=\arctan(\kappa L)$，$L$ 为轴距。它的直观含义是：**前视距离直接决定切角程度。** 在半径为 $R$ 的圆弧路径上稳定跟踪时，稳态横向误差近似满足

$$e_{ss}\approx\frac{L_d^{2}}{2R}.$$

代入 $R=5\ \text{m}$：

| 前视距离 $L_d$ | 近似稳态误差 $e_{ss}$ | 行为表现 |
| --- | --- | --- |
| 0.5 m | 0.025 m | 精度高，但易振荡、对噪声敏感 |
| 1.0 m | 0.10 m | 常用折中 |
| 2.0 m | 0.40 m | 转弯“抄近道”，窄道易撞内侧 |
| 4.0 m | 1.60 m | 几乎沿弦切过去，跟踪失效 |

由此得到两条实用规则：误差随 $L_d$ **平方**增长，所以宽容差时不要简单放大 $L_d$；低速可以取小 $L_d$，高速必须取大 $L_d$ 否则闭环增益过大导致蛇形。常见做法是自适应前视 $L_d=k v+\Delta_0$，其中 $v$ 为线速度，$k$ 约 0.3–1.0 s，$\Delta_0$ 为最小前视。

**Stanley 控制器** 用前轴中心到路径的横向误差 $e$ 和航向误差 $\psi_e$ 直接构造转角：

$$\delta=\psi_e+\arctan\!\left(\frac{k\,e}{v+\epsilon}\right),$$

$k$ 为横向增益，$\epsilon$ 防止低速时除零。它的横向误差近似按 $\dot e=-k\,e$ 收敛，即时间常数约 $1/k$：$k=2$ 时约 0.5 s 收敛到初值的 37%。

| 维度 | Pure Pursuit | Stanley |
| --- | --- | --- |
| 控制目标 | 跟踪前视点 | 直接压小横向误差 |
| 关键参数 | 前视距离 $L_d$ | 横向增益 $k$ |
| 低速表现 | 需减小 $L_d$，否则迟钝 | 好，$\epsilon$ 保证数值稳定 |
| 高速表现 | 需增大 $L_d$ 抑制振荡 | 增益需随 $v$ 下降 |
| 稳态误差 | 圆弧上近似 $L_d^2/(2R)$ | 理论上可收敛到 0 |
| 实现复杂度 | 低（一段几何） | 中（需航向误差与积分项） |
| 适用底盘 | 差速、阿克曼 | 主要阿克曼（前轮转向） |

一个最小可运行的 Pure Pursuit 转向计算如下：

```python
import math

def pure_pursuit_steer(pose, target, wheelbase):
    # pose: (x, y, theta); target: lookahead point in world frame
    dx, dy = target[0] - pose[0], target[1] - pose[1]
    dist = math.hypot(dx, dy)
    if dist < 1e-6:
        return 0.0
    # angle of target in robot frame
    alpha = math.atan2(dy, dx) - pose[2]
    alpha = math.atan2(math.sin(alpha), math.cos(alpha))  # wrap to [-pi, pi]
    curvature = 2.0 * math.sin(alpha) / dist
    return math.atan(curvature * wheelbase)
```

注意这里的前视点是**从路径上按弧长找**的，不是“最近的路径点”，否则 $L_d$ 会随进度变化而抖动。

## 动态障碍会触发短期避让或重新规划

局部层通常先尝试绕开突然出现的障碍；若前方通道持续被封堵、路径已经明显不可达，则需要通知全局层重新规划。是否重规划可以依据局部控制失败时间、路径阻塞程度或进度停滞判断。

三类触发条件及其阈值设计：

| 触发条件 | 判据 | 阈值建议 | 误触发风险 |
| --- | --- | --- | --- |
| 卡死超时 | 位移 $<0.05\ \text{m}$ 持续 $T$ | 2–5 s | 过短会把正常减速当卡死 |
| 路径阻塞 | 全局路径被障碍覆盖长度 $>0.5\ \text{m}$ | 0.5 m | 过高会长期贴着障碍走 |
| 进度停滞 | 到目标距离 $\ge$ 5 s 未下降 | 5 s / 10% | 过敏感导致频繁重算 |

局部层本身也要有“保守模式”：检测不到可行速度就把指令降到零并上报，而不是输出一个勉强可行但接近碰撞的解。

## 导航调试要沿数据流逐层定位

机器人不动时，可以按顺序检查：

1. 定位是否稳定；
2. 目标是否在正确坐标系；
3. 全局路径是否生成；
4. 局部控制器是否输出速度；
5. 安全层是否把命令拦截；
6. 底盘是否执行实际命令。

这样比直接更换规划算法有效得多。很多导航故障最后只是 TF、时间戳或控制接口问题。

## 调参与分层分工

三层各自的可调量完全不同，混着调几乎必然失败：

| 层 | 该调什么 | 不该用这一层解决什么 | 观测指标 |
| --- | --- | --- | --- |
| 定位 | 传感器权重、外参、滤波增益、时间同步 | 路径跟踪的蛇形 | 位姿协方差、与真值/回环的偏差 |
| 规划 | 分辨率、膨胀半径、启发权重、重规划阈值 | 稳态横向偏差 | 路径长度、扩展节点数、规划耗时 |
| 控制 | 前视距离/横向增益、$k_p,k_i,k_d$、限幅 | 定位漂移导致的系统性偏移 | 横向误差 $e$、超调、调节时间 |

**调参顺序：数据链 → 模型 → 控制器。**

1. **先修数据链**：确认 TF 时间戳、传感器频率、坐标系一致。这一步不修，后面所有调参都是在拟合噪声。
2. **再验模型**：发一个已知速度指令，测量实际位移，标定轮径、轴距、速度缩放系数。若“给 0.5 m/s 实际走 0.62 m/s”，控制器再准也没用。
3. **最后调控制器**：固定其他层，只调一组参数，用同一段路径复现。先调 $k_p$ 到略欠阻尼，再调 $L_d$ / 增益，最后加 $k_i$。

现象与所属层的对照：

| 现象 | 该调哪一层 |
| --- | --- |
| 沿直线走但整体平移了 0.4 m | 定位（或外参） |
| 直线走得歪，随速度变化 | 控制（前视/增益） |
| 到达目标后小幅来回摆 | 控制（$k_d$ 偏小或 $L_d$ 偏小） |
| 始终差 0.2 m 到不了目标 | 控制（$k_i$）或目标点位置 |
| 每次都在同一处“找不到路” | 规划（膨胀半径/地图） |
| 路径每 2 s 跳一次 | 规划（重规划阈值过敏感） |
| 速度指令有、轮子不转 | 驱动/数据链（不是控制器） |

隔离变量法：一次只改一个参数，其余冻结，用**同一初始位姿、同一路径、同一速度**重复 3 次，比较横向误差的均值与峰值。要求同时记录**均值**（看稳态）与**峰值/超调**（看瞬态），只看平均值会漏掉振荡。

## 实机导航失效的典型模式

仿真里跑通不等于实机能跑。下面这张表把最常见失效现象对到最可能的根因和第一个要验证的量：

| 现象 | 最可能原因 | 先验证什么 |
| --- | --- | --- |
| 机器人原地不动，无报错 | 安全层/急停拦截，或控制频率掉下 | 打印安全层状态与各节点频率 |
| 走一段后突然偏出几米 | 里程计累积漂移、无回环修正 | 对比定位输出与外部真值 |
| 转向总是慢半拍 | 控制延迟或时间戳错位 | 记录指令发出到轮速响应的时间差 |
| 高速时蛇形振荡 | 前视距离/增益未随速度自适应 | 检查 $L_d$ 是否随 $v$ 变化 |
| 窄通道必然卡住 | 膨胀半径 + 定位协方差过大 | 打印该处可通行宽度与定位 $\sigma$ |
| 目标点在前方却“不可达” | 目标落在膨胀障碍或地图外 | 检查目标点在代价地图上的取值 |
| 避障时贴着障碍擦过 | 软约束安全距离过小 | 检查最小离障碍距离统计 |
| 偶尔丢一帧就失控 | 无超时保护、状态机未降级 | 检查传感器超时处理与降级逻辑 |
| 到目标附近来回摆 | 目标容差小于控制精度 | 对比到达容差与稳态横向误差 $e_{ss}$ |

这套对照的价值在于：**它把“换个算法试试”变成“先测一个量”。** 大多数实机导航问题发生在数据链和控制参数，而不是规划算法本身。

## 真正可靠的导航还需要恢复行为

现实中会出现局部地图异常、机器人被卡住、目标暂时不可达。系统应能够检测“长时间没有进度”，并执行清障、后退、重新定位、重新规划或请求人工干预。恢复机制不是附属功能，而是让机器人从一次性 Demo 变成长时间自主系统的关键。

恢复行为本身也需要顺序与上限：先原地清理代价地图 → 小幅后退或转向脱离 → 重新定位 → 重新规划 → 请求人工。每一级要有次数上限（如后退 3 次后升级），否则机器人会在“后退—重规划—再卡住”的循环里空耗；同时每次恢复都应记录日志，方便离线统计哪一级最常触发。

## 进度监测连接规划与恢复

导航系统需要定义可测量的进度，例如到目标距离是否下降、沿路径是否前进、控制命令是否产生实际位移。只有明确进度指标，系统才能区分短暂停顿与真正卡住，并在合适时间触发清障、后退或重新规划。

一个直接的进度指标是到目标距离的滑动窗口下降率：

```python
import math
from collections import deque

class ProgressMonitor:
    def __init__(self, window=20, min_rate=0.02, dt=0.1):
        self.hist = deque(maxlen=window)  # (distance, has_moved)
        self.min_rate = min_rate          # m/s of closing speed
        self.dt = dt

    def update(self, pose, goal, cmd_speed):
        d = math.hypot(goal[0] - pose[0], goal[1] - pose[1])
        self.hist.append((d, abs(cmd_speed) > 0.01))
        if len(self.hist) < self.hist.maxlen:
            return "running"
        closing = (self.hist[0][0] - self.hist[-1][0]) / (self.dt * len(self.hist))
        if closing < self.min_rate and any(m for _, m in self.hist):
            return "stuck"      # commanded motion but no progress
        return "running"
```

关键判据是“有指令但无位移”：若指令速度接近零，说明系统在有意等待，不该算卡死；只有当 `cmd_speed` 非零而距离长期不下降时才触发恢复。这个区分能显著降低误触发。
